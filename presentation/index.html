Challenge 1: Grimoire Heap

PWN — Use-After-Free + Tcache Poisoning


Vulnerability

  • free() without nulling pointer → UAF
  • Read/write freed heap chunks
  • Flag stored on heap via malloc(0x80)

Exploit Chain

  1. Allocate 2 spells (size 0x80)
  2. Free A → leak heap_hi
  3. Free B → decode tcache fd
  4. Tcache poison → redirect to flag
  5. Allocate → read flag

Heap Layout

┌─────────────────┐
│   g_flag chunk   │ ← flag here
│   (0x90 bytes)   │
├─────────────────┤
│   Spell A        │ ← freed (UAF)
│   (0x90 bytes)   │
├─────────────────┤
│   Spell B        │ ← poisoned fd
│   (0x90 bytes)   │
└─────────────────┘

Challenge 2: Sandworm VM

PWN — VM Out-of-Bounds Escape


Vulnerability

  • Bounds check validates base register only
  • Final index = base + imm + 16 can exceed sandbox
  • 255 + 1 + 16 = 272 → hook function pointer

Exploit (6 instructions)

MOV  r0, 255       ; valid base
RLOAD r1, [272]    ; OOB read hook
ADD  r1, 0x1e0     ; → emit_flag
RSTORE [272], r1   ; OOB write
CALL hook          ; emit_flag()!
HALT

VM Memory

vm+0x000  registers[16]
vm+0x080  memory[256 cells]
          ↑ sandbox boundary
vm+0x880  hook_default ptr   ← cell 272
vm+0x888  hook argument
vm+0x890  bytecode

Key insight: Redirect hook_default (+0x1e0 → emit_flag) via OOB memory write


🚩 UCSI26{sandworm_vm_oob_escape_025a2ef7}

Challenge 3: Saturn Exchange

WEB — Async Settlement Race Condition


Vulnerability

Withdrawal balance check is not atomic. Concurrent requests all see 1.0 BTC and pass validation before settlement processes them.


Race Timeline

Time →
Req 1: check(1.0 > 0.6) ✓ → queued
Req 2: check(1.0 > 0.6) ✓ → queued
Req 3: check(1.0 > 0.6) ✓ → queued
                    ↓ settlement
         1.0 - (3 × 0.6) = -0.8 BTC
                    ↓
         🚩 FLAG DISCLOSED

Exploit

  1. Reset: POST /api/reset
  2. Fire 3× concurrent POST /api/withdraw
  3. Wait for settlement
  4. Check: POST /api/balance

Used aiohttp for true concurrent connections, maximizing the race window.


🚩 UCSI26{4sync_settlement_r4c3_110cbe1e}

Vulnerability

Challenge 6: OldStock Router

FIRMWARE — Custom Offset SquashFS Extraction


Analysis & Identification

  • Firmware binary file has a generic 256-byte header
  • SquashFS magic signature hsqs identified at offset 0x100
  • Root filesystem uses gzip compression metadata

Extraction & Recovery

  1. Inspect firmware headers via hex signature parsing
  2. Extract root filesystem with offset:
    3. unsquashfs -d out -o 256 FW.bin
  3. Scan files and locate etc/config/rconfig.bak
  4. Recover credentials and leaked access code flag

Backup Leak

# etc/config/rconfig.bak
config backup 'secrets'
    option ssid 'OldStock-F9D2'
    option flag 'UCSI26{0ld5t0ck_fw_b4ckup_l34k}'
    option psk 'not-the-flag'

Challenge 7: StaffDesk

WEB — GraphQL IDOR & Takeover Account Reset


Vulnerability

  • GraphQL query user(id: Int!) lacked object-level authorization
  • Any user could fetch details of administrator (user ID 1)
  • The fetched User object exposed the sensitive resetToken field

Exploit Chain

  1. Register normal user and retrieve session token
  2. Query user ID 1 and leak admin's password resetToken
  3. Invoke resetPassword mutation immediately to hijack account
  4. Submit protected flag query with the admin bearer token

Leaked Schema Fields

type User {
  id: Int
  username: String
  resetToken: String  # ← Leaked via IDOR!
}

type Query {
  user(id: Int!): User
  flag: String
}

Docker Sandbox Isolation

Safely executing generated exploit code and binaries


Why Sandboxing?

CTF solvers generate and run untrusted exploit payloads. Running this directly on the host poses massive security risks. The harness isolates execution via containers.


Sandbox Configuration

  • Volume Bindings: Mounts workspace (Read/Write) and challenge distfiles (Read-Only).
  • Strict Limits: Restricts memory (default: 4GB) and CPU footprint.
  • Security Profiles: Runs with unconfined seccomp/ptrace capabilites for low-level debugging (GDB, checksec) when required.
  • Host Fallback: Soft degradation to local execution when Docker is unavailable.

Anti-Loop Protection

Preventing LLMs from getting stuck in repetitive execution cycles


The Infinite Loop Problem

When a tool call fails, an LLM often repeats the same action with the same parameters (e.g. reading the same file 5 times), exhausting context windows and token budgets.


Warning Injection System

  • Sliding History: Keeps a sliding window of recent tool call names + argument hashes.
  • Warning State: Triggers warning prompt after 3 repeated calls to redirect the agent's strategy.
  • Break State: Terminates iteration after 5 repeated calls to conserve API token costs.

Injected Alert

⚠️ Loop Detected

"You appear to be repeating the same actions. Stop and reconsider your approach. Try a completely different technique or tool. Analyze why it is failing and pivot."


This feedback forces the LLM to dynamically adapt its reasoning and try creative alternatives.

Design Decisions


ReAct over Chain-of-Thought
ReAct enables tool use between reasoning steps, essential for interactive exploitation
LangGraph over raw loops
State machine provides clear control flow, conditional routing, and built-in tool execution
Provider abstraction
Swap between GPT-4o, Claude, and open-source Llama 3.1 with a single env var change
Category-specific prompts
PWN and WEB challenges need different knowledge — prompts are tailored per category
Subprocess sandboxing
Exploit code runs in isolated processes with timeouts to prevent agent self-compromise
Automatic flag detection
Regex UCSI26\{...\} scans all tool outputs — agent stops immediately on match
